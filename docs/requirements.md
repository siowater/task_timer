# Project Specification: Hierarchical Time Tracker App

## 1. プロジェクト概要
ユーザーが定義した最大4階層のカテゴリー（フォルダ）構造に基づき、タスク（学習・作業項目など）ごとの時間を計測・蓄積するスマートフォンアプリ。
日々の学習時間などの累積を目的としており、今日や今週といった期間ごとの稼働履歴を正確に記録・閲覧できる。
※初期フェーズでは上位カテゴリーへの時間の自動合算（ロールアップ）は行わず、カテゴリーは純粋な「タスクの分類フォルダ」として機能する。

## 2. フロントエンド技術要件 (Modern React Native)
- **Framework:** React Native (Expo SDK 52+)
- **Language:** TypeScript
- **Navigation:** Expo Router (ファイルベースルーティング)
- **State Management:** Zustand
- **Styling:** NativeWind (Tailwind CSS for React Native)
- **UI Architecture:** Functional Components & Hooks

## 3. データ永続化・アーキテクチャ方針
- **Persistence:** react-native-mmkv
  - Zustandの `persist` ミドルウェアを使用し、Store全体（ツリー構造および履歴データ）をJSONとしてMMKVに同期する。
- **Data Architecture:**
  - RDBは使用せず、単一のステートツリーとしてメモリ上に展開する。

## 4. データ構造・制約
### 4.1 階層構造とアイテム配置
- **Level 1〜4:** Categories（階層の深さは最大4階層まで）
- **Item:** Task (計測対象)
- **配置ルール:** Taskは特定の階層に依存せず、Level 1〜4のどのカテゴリーの直下にも自由に作成・配置が可能。
  - **ルート配置:** どのカテゴリーにも属さない「ルート（階層0）」の画面にも、直接Taskを作成・配置することができる。

### 4.2 アイテム数の制約とステータス
- **タスク数上限:** アプリケーション全体で作成できる「アクティブなTask」は**最大20個**まで。Categoryの作成数に制限は設けない。
- **アーカイブ（完了）機能と復元:**
  - 完了したTaskはアクティブなTaskの「20個」の上限カウントから除外され、過去の稼働履歴は引き続き閲覧できる。
  - **復元時の制約:** アーカイブ済みTaskをアクティブに復元する際、現在のアクティブTaskが20個に達している場合は復元不可とし、エラーToast（「アクティブなタスクが上限の20個に達しています。復元するには他のタスクを完了または削除してください」）を表示する。

## 5. 機能要件
### 5.1 タイマーロジックとバックグラウンド処理
- **計測:** Task単位でStart/Stop。複数のTaskの同時稼働が可能。
- **耐障害性:** サスペンドやタスクキルに対応するため、開始時に `startTime` を保持し、アプリ復帰時に現在時刻との差分から経過時間を計算する。
- **セッション上限と処理順序:**
  - タイマー放置を防ぐため、1回の計測は**最大24時間**を上限とする。
  - **計算順序:** 計測停止時（またはアプリ復帰時）、まず「経過時間が24時間を超えていないか」を判定する。超えていた場合は計測時間を24時間に丸め、Toast（「計測が24時間を超えたため、24時間で自動停止し記録しました」）を表示する。その後、以下の「日またぎ処理」を適用する。

### 5.2 稼働履歴と時間管理（ログ記録）
- **履歴の保持:** 「いつ・どのタスクを・何分行ったか」のセッションログを記録する。
- **日またぎの処理（自動・手動共通）:**
  - 自動計測の停止時、および**手動での時間入力時**において、記録対象の時間が0時（日付変更線）をまたいでいる場合、システム内部で自動的に「前日分のログ（〜23:59）」と「当日分のログ（0:00〜）」の2つのレコードに分割して保存する。
- **期間ビュー:** 蓄積した履歴データを基に、「今日」「今週」などの期間ごとの稼働実績を閲覧できる。

### 5.3 編集モード
- **並び替え:** Drag & Dropでの並び替えが可能（同一階層・同一カテゴリー内での順序入れ替えのみ）。
- **削除と連動仕様:**
  - **Taskの削除:** Taskを「削除」した場合、紐づく稼働履歴も完全に消去される（物理削除）。
  - **Categoryの削除:** Category内に「Task（アーカイブ済み含む）」または「子Category」が存在する場合は削除不可とし、エラーToast（「カテゴリー内にタスクまたは子カテゴリーが存在するため削除できません。中身を空にしてください」）を表示する。
- **手動修正:** 手動での時間追加・修正・過去の履歴の編集。

### 5.4 バリデーション (Validation Rules)
1.  **入力必須:** 空文字・空白のみの禁止。
2.  **時間整合性:** 未来の日付禁止、開始時刻 > 終了時刻の禁止、負の時間の禁止。
3.  **構造制約:** 新規Task追加時に「アクティブTaskが全体で20個以内か」を判定。

## 6. UI/UX要件
- **Categoryの表示:** Categoryは純粋な分類フォルダとして扱い、Categoryごとの合計学習時間などはUI上に表示しない。
- **アーカイブタスクの表示:** アーカイブ済みのTaskは別画面に分けず、現在の階層（ルートまたは各カテゴリー内）のリスト下部に「完了済み」としてグレーアウト等のスタイルで同居表示させる。物理削除や復元はここから行う。
- **第4階層のUI制限:** ユーザーが現在第4階層（Level 4）の画面を開いている場合、これ以上の深掘りを防ぐため「新規カテゴリー追加」ボタンを非表示（または無効化）にする。
- 直感的なドリルダウン遷移と、エラー時の即時フィードバック (Toast等)。

## 7. テスト・品質保証 (Testing Strategy)
**本プロジェクトは TDD (Test-Driven Development) で進行する。**

- **Tools:** Jest
- **Scope (Backend Logic):**
  - **Store Logic:** ZustandのState更新（追加、削除、アーカイブ、復元、時間ログの記録）のロジックテスト。
  - **Validation:** 「アクティブTask20個上限（追加・復元時）」「Category削除時の空チェック」の単体テスト。
  - **Time Calculation:** 「最大24時間制限でのカット」が先に行われ、その後に「日またぎのログ分割」が正しく行われるかの計算ロジック検証（手動入力時の分割も含む）。
- **Process:**
  1.  機能実装の前に、要件を満たすテストコード（失敗するテスト）を先に作成する。
  2.  テストを実行し、失敗を確認する。
  3.  テストを通過させるための実装を行う。
  4.  リファクタリングを行う。
